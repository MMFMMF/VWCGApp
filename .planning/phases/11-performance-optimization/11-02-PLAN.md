<task type="auto">
  <name>Task 1: Audit and fix CLS-causing patterns across all marketing components</name>
  <files>
    src/components/marketing/SampleReport.astro
    src/components/marketing/Hero.astro
    src/components/marketing/MiniAssessment.astro
    src/components/marketing/ComparisonTable.astro
    src/components/islands/CounterIsland.tsx
    src/components/islands/GaugeIsland.tsx
    src/components/islands/ExpandableInsightCard.tsx
    src/components/islands/MiniAssessmentIsland.tsx
  </files>
  <action>
    Perform a systematic CLS audit across all v1.1 marketing components and React islands. For each file:

    1. **Animation property audit:** Search for any CSS transitions or animations that use layout-triggering properties:
       - BAD: width, height, top, left, right, bottom, margin, padding (causes layout recalculation)
       - GOOD: transform (translate, scale, rotate), opacity (GPU-composited)
       - If found, replace with transform/opacity equivalents

    2. **Image dimension audit:** Check all `<img>` tags have explicit `width` and `height` attributes. Check all inline SVGs have width/height or viewBox. If missing, add appropriate dimensions.

    3. **Client directive audit:** Verify ALL React islands on the landing page (index.astro) use `client:visible`:
       - CounterIsland (Hero.astro) — should be client:visible
       - GaugeIsland (SampleReport.astro) — should be client:visible
       - ExpandableInsightCard (SampleReport.astro) — should be client:visible
       - MiniAssessmentIsland (MiniAssessment.astro) — should be client:visible
       If any use client:load, change to client:visible (all are below or at fold).

    4. **Expandable content audit:** Verify ExpandableInsightCard uses grid-template-rows (0fr/1fr) for expand/collapse, NOT max-height or height animation (which causes CLS).

    5. **Counter/Gauge hydration audit:** Verify CounterIsland and GaugeIsland reserve their visual space before hydration (explicit height/min-height on container) so hydration doesn't cause layout shift.

    6. **MiniAssessment layout stability:** Verify the MiniAssessmentIsland container has a fixed or min-height so question transitions don't cause layout shift. The wizard should transition within a fixed-size container.

    For any issues found, make the minimal fix. If NO issues found (all patterns already correct from Phase 8 implementation), document that the audit passed with zero changes needed.

    WHY this audit matters: CLS > 0.1 is a Core Web Vitals failure. Layout shifts from animations, unhinted images, or hydration are the most common causes on Astro + React Islands sites.
  </action>
  <verify>
    1. Grep for CSS properties that cause layout shift in marketing components:
       `grep -rn "transition.*\(width\|height\|top\|left\|margin\|padding\)" src/components/marketing/ src/components/islands/`
       — should return zero results (or only in grid-template-rows context)
    2. All client:visible directives confirmed on landing page islands
    3. `npm run build` passes
  </verify>
  <done>
    All marketing components and React islands audited for CLS-causing patterns. Zero layout-shifting animations found (or all fixed). All images have dimensions. All below-fold islands use client:visible. Build passes.
  </done>
</task>

<task type="auto">
  <name>Task 2: Run Lighthouse mobile audit and document baseline metrics</name>
  <files>
    (no files modified — measurement task)
  </files>
  <action>
    1. Build the production site: `npm run build`

    2. Start the preview server: `npx astro preview` (runs on localhost:4321)

    3. Run Lighthouse CLI mobile audit against the landing page:
       ```bash
       npx lighthouse http://localhost:4321 \
         --emulated-form-factor=mobile \
         --throttling.rttMs=150 \
         --throttling.throughputKbps=1638 \
         --throttling.cpuSlowdownMultiplier=4 \
         --output=json \
         --output=html \
         --output-path=./lighthouse-report \
         --only-categories=performance \
         --chrome-flags="--headless=new --no-sandbox"
       ```
       Note: If lighthouse CLI is not available globally, install: `npx -y lighthouse@latest`

    4. Extract and document key metrics from lighthouse-report.json:
       - Performance score (target: > 80)
       - LCP in seconds (target: < 2.5s)
       - CLS score (target: < 0.1)
       - FCP in seconds (informational)
       - TBT in milliseconds (informational)
       - Speed Index (informational)

    5. Compare bundle sizes to v1.0 baseline:
       - Open dist/stats.html (from Plan 01's visualizer)
       - Document total JavaScript bundle size
       - Document the ~16KB v1.1 additions
       - Verify total JS increase < 100KB from v1.0 baseline

    6. If Lighthouse mobile score is BELOW 80:
       - Identify the top 3 Lighthouse opportunities
       - Document specific recommendations
       - Note: Further optimization may be needed in a gap-closure plan

    7. If Lighthouse mobile score is ABOVE 80:
       - Document the passing metrics
       - Note the margin above the threshold

    IMPORTANT: Lighthouse scores vary by ~5 points between runs. Run the audit 2-3 times and use the median score. If scores are borderline (78-82), note the variance.

    WHY Lighthouse CLI: Provides consistent, reproducible mobile performance testing with standardized 3G throttling. PageSpeed Insights online tool can be used for final validation but CLI gives us immediate, repeatable local results.
  </action>

    4. LCP, CLS, FCP, TBT documented

  </verify>

  </done>
